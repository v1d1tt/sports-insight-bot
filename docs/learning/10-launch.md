## 1. How the demo video was made

The video ([docs/demo/sports-insight-bot-demo.mp4](../demo/sports-insight-bot-demo.mp4), 24.8 s, 1920×1080, 30 fps, 3.5 MB) shows the **live production site**, not a mock. Five steps:

1. **Record the real app.** A Playwright script (`@playwright/test` 1.65.1, headless Chromium) opens https://sports-insight-bot.vercel.app and does what a Visitor does: types a question, attaches a scorecard image, asks for a T20 powerplay field, drags fielders out of the 30-yard circle until the rule warning shows, taps seven Shots into a Wagon wheel, and repeats the Wagon wheel at phone width with touch taps.
2. **Capture frames with their times.** Playwright's own `recordVideo` gives a low-quality WebM. Instead, the script opens a Chrome DevTools Protocol session (`context.newCDPSession(page)`) and calls `Page.startScreencast` (JPEG, quality 92). Chrome sends a `Page.screencastFrame` event each time the page paints, with a timestamp. The script saves each frame and its time, and writes a mark ("chat-sent", "field-done", "warned", ...) at each step.
3. **Cut and speed up.** A small Python file maps each output frame (30 per second) to a source time. Each scene is a list of pieces such as "source 14.3 s to 35.1 s, played in 2.5 s". So a 20-second model answer plays in 2.5 s, and the drag plays slower than real time so the eye can follow it.
4. **Compose in a browser.** One HTML page draws each output frame: the recorded frame on the "Scorer's book" ruled paper, and a caption in the app's own fonts (Big Shoulders Display and Public Sans, loaded from `node_modules/@fontsource-variable`) and colours (from `frontend/src/app.css`). Every animation is a pure function of the frame time, so Playwright can screenshot frame 0, 1, 2, ... in any order and the result is the same. Between scenes the old scene fades out to the paper and the new one comes in, so two busy screens never overlap.
5. **Sound and encode.** The music is generated by a short NumPy script: a D-major loop (D, Bm, G, A) at 112 BPM with a soft kick, bass, pad and a plucked arpeggio, plus a quiet "pencil tick" on each cut, tuned to the same key. Generated audio has no licence question, which matters because the video sits in a public repo. ffmpeg (9.0.2) encodes H.264 + AAC with `+faststart`, so the file starts to play before it has fully downloaded. Frame 0 is replaced with the best still (the red rule warning), so every player shows that as the thumbnail; replacing the frame (not adding one) keeps the length and the audio in sync.

**Cost and limits.** The Vercel firewall allows 20 chat requests per IP in 10 minutes. The recording used 9: three runs × three requests (chat, image, field). Two runs failed late in the script (the phone drawer was already open; a click landed while the page still scrolled). The fix: save the frame times after every step (not only at the end), and record the scenes that need no model request (Wagon wheel, phone) in a separate script that refuses to send any `/api/chat` request, so it can run again for free.

**The scorecard in the video is fictional** (made-up teams and players, drawn as HTML by the script), so no real data or third-party image is in the video.

## Interview questions

**1. Walk me through what happens when a Visitor asks for a field.**
The page sends the last 20 Messages and the Sport focus as a POST to `/api/chat`. The Vercel firewall checks the rate limit. The input guard checks sizes and types and, for risky input, asks a safeguard model whether it is a prompt injection. The Analyst streams the model's reply as server-sent events. When the model calls the `show_field_placement` tool, the server checks the field (11 fielders, known names, sides, Fielding restrictions from `restrictions.json`); a bad field goes back to the model once with the reasons. Only a checked field reaches the page, which draws it as SVG and saves it to IndexedDB. Dragging and the live rule check then run in the browser from the same `restrictions.json`, with no request.

**2. Why is there no database?**
Chats are personal and the app has no accounts. Keeping them in the browser's IndexedDB means the server holds no personal data, two Visitors can never see each other's Chats, and the API is stateless, which suits serverless functions. The cost: Chats do not move between devices, and clearing site data deletes them. ADR 0001 records this.

**3. How do you know the server's rule check and the browser's rule check agree?**
Both read one data file, `restrictions.json`, and both run the same table of test cases, `fielding_cases.json`: pytest on the server and Vitest in the browser. If someone changes a limit in one place only, a test fails. ADR 0003 records this.
